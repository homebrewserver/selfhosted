SSH is how you run commands on your home server from another computer. This guide explains what happens when you connect, then sets up key-based login, a short alias for your server, password login switched off, protection against password-guessing bots, and SSH tunnels to reach services you don't want on the internet. How SSH works SSH (Secure Shell) opens an encrypted connection between a client, the computer you type on, and a server, the machine you want to control. Everything that passes through it, including your password if you use one, is encrypted. Almost every Linux server and every current desktop operating system ships OpenSSH, the most widely used implementation. Two kinds of key pair are involved, and keeping them apart makes everything else easier to follow: Host keys belong to the server. They prove to your client that it is talking to your server and not to something pretending to be it. The server creates them when OpenSSH is installed. User keys belong to you. They prove to the server that you are allowed in, in place of a password. You create them on the computer you connect from. Each key pair has a private half and a public half. The private half never leaves the machine it was made on. The public half can be copied anywhere, because it can only check signatures, not make them. Install the SSH server On Debian and Debian-based systems, install the server package on the home server. Any of the machines in choosing home server hardware will do. Debian starts the service after installing it. On Debian 13, this installs OpenSSH 10.0, which listens on port 22. Your laptop or desktop already has the client: the ssh command is built into Linux, macOS and Windows 10 and later. Find the server's address on your home network with ip -brief address on the server. It will look like 192.168.1.20 . If the address changes after a reboot, give the server a fixed address in your router, as the port forwarding guide describes. First login and the host key fingerprint Connect from your computer with your username on the server and its address: The first time, the client cannot know whether the host key it receives is genuine, so it shows a fingerprint and asks whether to continue. To check it, run this on the server itself, at its own keyboard or through a connection you already trust: If the SHA256: value matches what the client showed, type yes . The client saves the key in ~/.ssh/known_hosts and checks it on every later connection. If it ever changes without a reason you know of (you reinstalled the server, for example), the client refuses to connect and shows a warning. Don't delete the old entry until you know why the key changed. Create a key pair On the computer you connect from, create a user key: Ed25519 is the default key type in current OpenSSH, so plain ssh-keygen gives the same result. The -C comment is a label that shows up in the server's key list, which helps when you later need to remove the key for a lost laptop. The command asks where to save the key (accept the default, ~/.ssh/id_ed25519 ) and for a passphrase. Set one. Without it, anyone who copies the private key file can use it. With it, the file is useless to them without the passphrase. An SSH agent remembers the unlocked key for your session, so you type the passphrase once, not on every connection. The agent runs by default on most desktops. You now have two files: ~/.ssh/id_ed25519 (private, keep it there) and ~/.ssh/id_ed25519.pub (public, safe to copy). Copy the public key to the server The server lets in any key listed in the user's ~/.ssh/authorized_keys file, one public key per line. The easiest way to add yours is ssh-copy-id , which logs in with your password one last time and appends the key: It also creates the ~/.ssh directory with mode 700 and the authorized_keys file with mode 600 if they don't exist yet. Those permissions matter: OpenSSH ignores the file if other users could change it. On Windows, which has no ssh-copy-id , paste the contents of the .pub file as a new line in ~/.ssh/authorized_keys on the server, then fix the permissions there: Log out and connect again. If you are asked for the key's passphrase (or nothing at all, when the agent has it) instead of the account password, the key works. Give the server a short name in ~/.ssh/config Typing the user and address every time is tedious. The client reads ~/.ssh/config on your computer, where you can give each server a short name and its settings: Now ssh homeserver connects with those settings, and so do scp , sftp and rsync when you use the same name. Add a Port line if the server listens on a different port. The ssh_config manual lists every option. Turn off password login Once key login works, turn off password login. A server that accepts passwords can be broken into by anyone who guesses one. A server that only accepts keys cannot be, in practice. Keep your current SSH session open while you make this change, and test from a second terminal. If something is wrong, you can still fix it from the first session instead of walking to the server with a keyboard. On Debian, the main file /etc/ssh/sshd_config starts with Include /etc/ssh/sshd_config.d/*.conf . For each setting, sshd uses the first value it reads, so a file in that directory takes priority over the main file and survives package upgrades. Create /etc/ssh/sshd_config.d/10-hardening.conf on the server: What each line does: PasswordAuthentication no stops the server from accepting passwords. KbdInteractiveAuthentication no closes the second route to a password prompt. Debian already sets it, and repeating it here costs nothing. PermitRootLogin no stops direct logins as root. Log in as yourself and use sudo . AllowUsers alice lets only the listed accounts log in over SSH. Put your own username here, and add others separated by spaces. Check the configuration before you apply it. sshd -t prints nothing when the syntax is fine, and sshd -T prints the settings sshd will actually use: From a second terminal, test both ways in. A key login should work as before. A forced password login should fail with Permission denied (publickey) : Password-guessing bots: OpenSSH penalties and fail2ban As soon as port 22 is reachable from the internet, bots start trying common usernames and passwords. With password login switched off they cannot get in, but they fill your logs and use a little processor time. OpenSSH now handles much of this itself. Since version 9.8, the server has a PerSourcePenalties setting that makes it refuse connections for a while from addresses that fail to log in, crash it, or connect without authenticating. It is on by default. On Debian 13, sshd -T shows these defaults: In plain terms, a client that disconnects after failed login attempts earns its address a 5-second penalty, penalties add up to at most 600 seconds, and an address is refused only once its penalty passes 15 seconds. For a home server with key-only login, this is often enough. fail2ban goes further. It reads the logs, counts failures per address and adds firewall rules that block an address for a set time. It can watch other services too, such as a web server or a mail server. On Debian 13, installing the package is enough to protect SSH: Debian's own file /etc/fail2ban/jail.d/defaults-debian.conf enables the sshd jail, reads the systemd journal and blocks with nftables. The defaults in jail.conf ban an address for 10 minutes after 5 failures within 10 minutes. To change them, create /etc/fail2ban/jail.local rather than editing jail.conf , then check the jail: Moving SSH to a port other than 22 cuts the noise in the logs, because most bots only try port 22. It does not add real security, and it means adding a Port line to every client config. Key-only login does the real work. The better question is whether SSH needs to face the internet at all. A VPN such as WireGuard or Tailscale lets you reach the server from outside without opening port 22. The port forwarding guide compares the options. SSH tunnels: reach a service without opening a port SSH can carry other network traffic through its encrypted connection. This is called port forwarding or tunnelling, and it is the safest way to reach an admin page that should never be on the internet. Local forwarding ( -L ) makes a port on your computer lead to a port on, or reachable from, the server. Say an admin page listens only on localhost:8080 on the server: While this runs, opening http://localhost:9000 on your computer shows the server's page. -N means "don't open a shell, just forward". Add -f to send it to the background. Dynamic forwarding ( -D ) turns the connection into a SOCKS proxy. ssh -N -D 1080 homeserver lets a browser set to use the SOCKS proxy localhost:1080 browse as if it were on your home network. That is useful for reaching your router's admin page while you are away. Remote forwarding ( -R ) works the other way round: a port on the server leads back to your computer. ssh -N -R 8080:localhost:3000 homeserver lets the server reach a service on your laptop's port 3000. Jump hosts ( -J ) connect through one server to reach another. ssh -J homeserver pi@192.168.1.30 reaches a second machine on your home network through the server. In ~/.ssh/config , the same thing is a ProxyJump homeserver line. Tunnels also let you manage an XMPP server 's admin interface, the OpenClaw web panel or any other local-only page without exposing it. The tunnel only stays up while the SSH connection does. Forwarding is allowed by default ( AllowTcpForwarding yes ). Ports opened with -R listen only on the server's localhost unless you change GatewayPorts , which defaults to no . When a connection fails Run the client with -v to see each step of the connection, including which keys it offers and why the server refused them: Common causes: Connection refused or timed out: sshd is not running ( systemctl status ssh on the server), a firewall blocks port 22, or you have the wrong address. Permission denied (publickey): the server did not accept any key offered. Check that the public key is in the right user's authorized_keys , that the permissions are 700 and 600 , and that your username is in AllowUsers . Host key verification failed: the server's host key differs from the one saved in known_hosts . If you know why (a reinstall), remove the old entry with ssh-keygen -R 192.168.1.20 . If you don't, stop and find out. On the server, sudo journalctl -u ssh shows why sshd refused a login. Frequently asked questions Which SSH key type should I use? Use Ed25519. It is the default key type in current OpenSSH, so ssh-keygen -t ed25519 and plain ssh-keygen create the same kind of key. Where do I put my public SSH key on the server? Add it as one line in ~/.ssh/authorized_keys in the home directory of the account you log in as. The ~/.ssh directory needs mode 700 and the file needs mode 600, or OpenSSH ignores it. How do I disable SSH password login on Debian? Create a file in /etc/ssh/sshd_config.d/ with PasswordAuthentication no and KbdInteractiveAuthentication no , check it with sudo sshd -t , then run sudo systemctl reload ssh . Test key login from a second terminal before you close your current session. Do I still need fail2ban if password login is off? Not strictly. OpenSSH 9.8 and later penalize addresses that fail to log in through PerSourcePenalties , which is on by default. fail2ban adds firewall rules that block an address for a set time, and it can watch other services too. What is the ~/.ssh/config file for? It stores per-server settings on your computer, such as the address, username, port and key file, under a short name. With an entry called homeserver , ssh homeserver connects with all those settings. How do I make an SSH tunnel to a service on my server? Use local forwarding: ssh -N -L 9000:localhost:8080 homeserver makes localhost:9000 on your computer lead to port 8080 on the server. The tunnel lasts as long as the SSH connection. Port forwarding tells your home router to pass certain incoming connections to your server, so people outside your home can reach the services it runs. This guide covers the checks to make first, the forwarding rule itself, how to test it from outside, dynamic DNS, and what to do when your connection makes forwarding impossible. Why a home server needs port forwarding Your internet provider gives your router one public IPv4 address. Every device in your home, including the server, gets a private address from the router, usually starting with 192.168. , 10. or 172.16. to 172.31. . These private ranges are defined in RFC 1918 and cannot be reached from the internet. The router translates between the two (network address translation, or NAT), so your devices can open connections out. Incoming connections are the problem. When a request arrives at your public address on, say, port 443, the router has no idea which device it is for, so it drops it. A port forwarding rule fills that gap: "send anything arriving on port 443 to 192.168.1.20, port 443". A port is a number from 1 to 65535 that tells a machine which program a connection is for. Some common ones for a home server: Only forward the ports a public service needs. Admin pages, databases and file shares should never be forwarded. Reach them through a VPN or an SSH tunnel instead. Check for CGNAT before you start Some providers no longer give each customer a public IPv4 address. They put many customers behind one shared address with carrier-grade NAT (CGNAT). Port forwarding on your router then does nothing, because the provider's NAT drops the connection before it reaches you. To check, compare two addresses: Find the WAN or internet address on your router's status page. Find your public address as the internet sees it. On the server, this asks an OpenDNS resolver to report the address your query came from: (On Debian, dig is in the bind9-dnsutils package.) If the two match, you have a public address and forwarding will work. If the router's WAN address is in 100.64.0.0/10 (from 100.64.0.0 to 100.127.255.255 ), you are behind CGNAT. That range is reserved for exactly this use by RFC 6598. A WAN address in one of the private ranges means another router sits between yours and the internet (double NAT). Behind CGNAT, ask your provider for a public IPv4 address. Some give one for free on request, some charge, some refuse. If you cannot get one, skip to the alternatives below. With double NAT, either set the first box (often the provider's modem) to bridge mode, or forward the port on both routers. Give the server a fixed address on your network A forwarding rule points at one private address. If the server gets a different address from the router after a reboot, the rule points at nothing. Fix the address first. The simplest way is a DHCP reservation (also called a static lease or address reservation) on the router. The router always hands the same address to the same network card, identified by its MAC address. Find the server's current address and MAC address on the server: Then, in the router's LAN or DHCP settings, add a reservation for that MAC address. Pick an address that the router does not hand out to other devices, or simply keep the one it already has. Reboot the server and check that it gets the reserved address. The other way is to set a static address in the server's own network configuration. That works too, but you must choose an address outside the router's DHCP range, or two devices may end up with the same one. Add the forwarding rule Log in to the router's web interface. Its address is usually the default gateway, which ip route show default on the server prints after via . The setting has different names by maker: "port forwarding", "virtual server", "NAT forwarding" or "port mapping". Some provider apps put it under "advanced" or "security". A rule has the same parts on every router: External port (or public port, WAN port): the port the outside world connects to, for example 443. Internal address : the server's reserved private address, for example 192.168.1.20. Internal port : the port the service listens on, usually the same as the external one. Protocol : TCP, UDP or both. Web servers and XMPP use TCP and WireGuard uses UDP. Choose only what the service needs. Save the rule. Before you test, make sure the service is actually running and listening on the server. ss lists listening ports and the program behind each: A line such as 0.0.0.0:443 or [::]:443 means the service listens on all addresses. 127.0.0.1:443 means it only accepts connections from the server itself, and forwarding will not help until you change that. Also check the server's own firewall: if it runs ufw, the port must be allowed there too. Turn off UPnP on the router unless you know you need it. UPnP lets any program on your network open ports on the router without asking you. Rules you add by hand are easier to keep track of. Test from outside your network Testing from inside your home often gives the wrong answer. Many routers do not support "hairpin NAT" (also called NAT loopback): a request from inside the network to your own public address never comes back in, even though the forwarding works for everyone else. Test from a different network instead. The easiest is a phone with Wi-Fi turned off, using mobile data. Open https://your-public-address or your domain in its browser, or use an SSH app to connect to the forwarded port. From a computer outside your home, nc -vz your-public-address 443 reports whether a TCP port is open. If the test fails, work through the chain from the server outwards: Does the service answer on the server itself ( curl http://localhost for a web server)? Does it answer from another device in your home on the server's private address? Does the server's firewall allow the port? Does the router rule point at the right address, port and protocol? Is the router's WAN address the same as your public address, or are you behind CGNAT? Does your provider block the port? Some providers block certain incoming ports on home plans, and their terms of service say which. If your router lacks hairpin NAT and you want to use your domain from inside the house, add a DNS entry for the domain on your local network that points to the server's private address. Many routers and local DNS filters can do this. Dynamic DNS: a name that follows your address Most home connections get a public address that can change, after a router restart or every so often. A domain name that points at the old address then leads nowhere. Dynamic DNS (DDNS) solves this: a small program checks your public address and updates a DNS record when it changes. You have three common options: The router's DDNS client. Many routers support a few DDNS providers in their settings. This is the easiest, but limits you to the providers the router knows. ddclient on the server. ddclient is an open-source DDNS client, packaged in Debian, that supports many providers and DNS hosts with an update API. Your DNS host's API. If your domain's DNS host has an API, a short script run by a timer can update the record. This is what most DDNS clients do internally. Use a low TTL (time to live) on a dynamic record, such as five minutes, so resolvers forget the old address quickly after a change. IPv6 works differently With IPv6 there is usually no NAT. Your provider gives your home a whole range of addresses, and every device, including the server, gets its own public one. Nothing needs to be "forwarded". Instead, the router's firewall blocks incoming IPv6 connections by default on most home routers, and you open a hole for one address and port. Look for "IPv6 firewall", "pinhole" or "allow incoming" in the router settings. Use the server's stable address, not a temporary privacy address, which changes over time. ip -6 address on the server lists both. The temporary ones are marked temporary . IPv6 helps if you are behind CGNAT for IPv4 and your provider gives you IPv6, because the IPv6 address is not behind the shared NAT. The catch is that visitors on IPv4-only networks still can't reach you, so IPv6 alone is not enough for a public website. When port forwarding is not possible If you are behind CGNAT, cannot change the router, or simply don't want open ports, there are three main alternatives. All three work by having your server make an outgoing connection, which NAT always allows, and receiving traffic back through it. A private VPN: WireGuard or Tailscale If only you and people you know need to reach the server, a VPN is the best fit. Your devices join a private network with the server, and nothing is exposed to the internet. WireGuard is a small, fast VPN built into the Linux kernel. On its own, it needs one side to be reachable, which means a forwarded UDP port at home or a small rented server in the middle. Tailscale builds on WireGuard and adds a coordination service that connects your devices through most NATs, including CGNAT, without any forwarded port. Its coordination server is run by Tailscale. Headscale is an open-source, self-hosted replacement for it if you want no third party involved. The limit: every device must run the VPN client, so this does not work for a public website or for friends on other XMPP servers. Tailscale's Funnel feature exposes a service to the public internet, but only on ports 443, 8443 and 10000, with bandwidth limits you cannot change. The Funnel relay cannot decrypt the traffic: your device handles the TLS. Cloudflare Tunnel Cloudflare Tunnel runs a program called cloudflared on your server. It makes outgoing connections to Cloudflare's network, and Cloudflare sends visitors to your site through them. You need no public IP and no open ports, and it works behind CGNAT. The trade-offs: Cloudflare handles two separate connections, one with the visitor and one with your server. It sits in the middle of the traffic and can read it. Your site depends on a large company's free plan, whose terms can change. Cloudflare's terms for its free CDN say you may not use it to serve video or a "disproportionate percentage" of pictures, audio or other large files unless you use its paid services. A photo gallery or media server may break those terms. It is built for HTTP. Other protocols, such as XMPP server-to-server traffic, need a different route. For a small public website behind CGNAT it is the quickest fix. If you care about who sees your traffic, which is one reason to self-host at all, the next option fits better. A small rented server as a relay Rent the smallest virtual server you can find, which has a public IP. Connect your home server to it with WireGuard, started from the home side so CGNAT does not matter. Then forward ports on the rented server through the tunnel to your home server, or run a reverse proxy there. This works for any protocol and keeps TLS on your own machine, so the relay only passes encrypted bytes for HTTPS. It costs a monthly fee and is more work to set up and keep updated. Your connection still depends on the relay staying up. Keep the exposed parts safe Bots scan public addresses for open ports all the time, so every forwarded port will be tried. A few rules keep the risk small: Forward only the ports a public service needs, and remove rules you no longer use. Keep the services behind those ports updated. The web server guide shows how to turn on automatic security updates on Debian. If you forward SSH, use key-only login, as the SSH guide explains, or keep SSH behind a VPN. Never forward the router's own admin page, a NAS admin page or a database port. Never forward a service that answers without a password. Ollama's API is one: it answered with no login in the OpenClaw and Ollama test , so keep its port 11434 off your router. With the port open and a name pointing at it, you can host a website or an XMPP chat server from home. If you are still choosing a machine to run them on, see choosing home server hardware . Frequently asked questions How do I know if I am behind CGNAT? Compare the WAN address on your router's status page with your public address as the internet sees it. If they differ and the router's address is in 100.64.0.0/10, you are behind CGNAT and port forwarding on your router will not work. Can I port forward behind CGNAT? Not on your own router, because your provider's NAT drops incoming connections first. Ask your provider for a public IPv4 address, or use a VPN such as Tailscale, Cloudflare Tunnel or a rented server as a relay. Why does my port forward work from outside but not from home? Your router probably lacks hairpin NAT, also called NAT loopback, so requests from inside to your own public address don't come back in. Test from a phone on mobile data, and add a local DNS entry for your domain that points to the server's private address. Is port forwarding safe? Bots scan public addresses all the time, so every forwarded port will be tried. Forward only the ports a public service needs, keep that service updated, use key-only login for SSH, and never forward admin pages or databases. Do I need a static IP address to host a server at home? No. Give the server a fixed private address with a DHCP reservation on the router, and use dynamic DNS so a domain name follows your public address when it changes. Is Cloudflare Tunnel better than port forwarding? It works behind CGNAT and needs no open ports. The trade-offs are that Cloudflare sits in the middle and can read the traffic, it is built for HTTP, and its free CDN terms restrict serving video and large numbers of large files. This guide sets up a web server on a Debian machine at home and serves a static website from it over HTTPS. It gives two routes, nginx with Certbot or Caddy, then covers the firewall, publishing updates to the site and keeping the server patched. Is hosting at home right for your site? A static website (HTML, CSS and images, no database) is the easiest thing to host from home. It needs little memory or processor time, and a small machine can serve it to many visitors. Blogs made with a static site generator such as Hugo, Jekyll or Eleventy fall into this group. Home hosting has limits you should accept before you start: Upload speed. Your visitors download from your upload, which on many home connections is much slower than the download speed. A page with large images will feel slow if several people load it at once. Uptime. When your power or internet goes down, so does the site. Nobody gets paged. Your connection. You need a way for visitors to reach the server, which usually means a public IP address and two forwarded ports. Check your provider's terms too, since some home plans restrict running servers. For a personal site, a project page or a small community, these limits are usually fine. For a shop or anything people depend on, rent hosting instead. Turn on the firewall A firewall on the server blocks every port you haven't chosen to open, so a program you install later doesn't end up on the internet by accident. ufw is the simplest way to set one up on Debian. Allow SSH before you enable the firewall. Enabling it first cuts off your SSH session, and you will need a keyboard and screen on the server to get back in. The default policy blocks incoming traffic and allows outgoing traffic. The rules apply to IPv4 and IPv6 alike. With nginx, sudo ufw allow "Nginx Full" does the same as the two port lines, since the profile opens 80 and 443 over TCP. sudo ufw app list shows the profiles your installed programs provide. Open https://example.org and check that: the page loads and the browser shows a valid certificate; http://example.org redirects to HTTPS; both example.org and www.example.org work. This guide compares the five kinds of machine people use as a home server: a Raspberry Pi 5, a new Intel N100 or N150 mini PC, a used office mini PC, an old laptop and a small NAS. At the end you will know which one fits the services you want to run, what it costs to keep on all year, and what to check before you buy. What a home server has to do A home server is a computer that stays on, sits in a cupboard or on a shelf, and runs services for you and the people you share them with. It might host a chat server, a small website, file sync, a password manager or backups. It rarely needs a screen or a keyboard once it is set up, because you manage it over the network with SSH . That use is different from a desktop's in four ways: It runs all the time. Idle power use matters more than peak performance, because the machine spends most of its life waiting for requests. It needs enough memory, not a fast processor. A handful of light services fits in 2 to 4 GB of RAM. Running many containers, a photo library or a media server needs more. It needs storage you can trust. Your data lives on it, so the drive and your backups matter more than raw speed. It needs a wired network connection. Ethernet is more reliable than Wi-Fi for a machine other people connect to. Most home services are light. A personal XMPP server or a static website uses very little processor time. The usual mistake is to buy more machine than the job needs and then pay for its idle power every hour of the year. A local AI model is the exception. The models in the Ollama vs llama.cpp test ran on a graphics card with 24 GB of its own memory, which none of the machines below has. Power use: the cost you pay every hour To turn a power figure into a yearly figure, multiply the watts by 8,760 (the hours in a year) and divide by 1,000. A machine that idles at 10 W uses about 88 kWh a year, and one that idles at 30 W uses about 263 kWh. Multiply by the price per kWh on your electricity bill to get the yearly cost. Published idle figures are a starting point, not a promise. They change with the operating system, the BIOS power settings, attached drives and even the mains voltage. One owner of a used Lenovo ThinkCentre M900 Tiny measured 6.5 to 7 W at the wall on Fedora Server at 240 V, and about 8 W on Windows 11. ServeTheHome had measured 11 to 13 W for the same model on a 120 V circuit. Running powertop --auto-tune on Linux cut the owner's figure by about half a watt. The only figure that counts is the one for your machine with your drives and your services. A plug-in power meter costs little and shows the real number. Measure the machine idle for a few minutes after boot, then again while it does its normal work. The figures quoted on this page come from the reviews and spec sheets listed under Sources. Treat them as rough guides. The gap between a Pi and a mini PC is a few watts at idle. Across a year, that is tens of kWh, not hundreds. Power use is a good reason to avoid a large old tower PC, but it should not stop you from picking a mini PC if you need what it offers. Raspberry Pi 5 The Raspberry Pi 5 is a single-board computer with a quad-core Arm Cortex-A76 processor at 2.4 GHz, Gigabit Ethernet and a choice of 1, 2, 4, 8 or 16 GB of memory. It has one PCIe 2.0 lane that takes an NVMe SSD through an M.2 HAT, and two USB 3.0 ports. It is the best fit when you want the lowest idle power and your services are light: DNS filtering, a chat server, a small website, a password manager, a few containers. It is silent with passive cooling and small enough to sit next to the router. Things to know before you buy one: Power supply. Raspberry Pi recommends its 27 W USB-C supply, which delivers 5 V at 5 A. With a 3 A supply, the board limits USB peripherals to 600 mA in total instead of 1.6 A, which can be too little for a USB hard drive. Storage. A microSD card works for trying things out. For a server that writes all day, boot from an NVMe SSD on an M.2 HAT+ or from a USB SSD instead. Arm, not x86. Much server software and many container images are built for 64-bit Arm, but some are only published for x86. Check that every program you plan to run has an Arm64 build. Power when off. A Pi 5 that is shut down still draws about 1 to 1.4 W by default. Setting POWER_OFF_ON_HALT=1 in the bootloader configuration brings this down to about 0.01 W. The full cost. Add the power supply, a case with cooling, and an SSD with its adapter to the board price before you compare it with a mini PC. New Intel N100 and N150 mini PCs Mini PCs built on Intel's N100 (launched in 2023) or N150 (launched in 2025) are the common choice for a first home server that needs more room than a Pi. Both chips have four cores and a 6 W processor base power, and both include Intel Quick Sync Video for hardware video transcoding. The N150 boosts to 3.6 GHz and the N100 to 3.4 GHz. They suit you if you want to run many containers, a media server that transcodes video, or software that only ships for x86. They usually come with an SSD, a case and a power supply in the box, so there is nothing else to buy. Points to check on a specific model: Memory limit. Intel lists a maximum of 16 GB and a single memory channel for both chips. Many models have soldered memory, so buy the amount you will need later. Idle power. Published figures for N100 boxes vary from model to model. ServeTheHome measured 10.5 to 12 W at idle on a fanless N100 firewall appliance with several network ports. A box with fewer ports and tuned power settings may draw less, so look for a measurement of the exact model. Fan noise. Many of these boxes have a small fan. Fanless models exist and suit a living room or bedroom better. Storage slots. Count the M.2 and 2.5-inch slots if you want a second drive for data. Used office mini PCs Businesses replace their small desktop PCs every few years, and the used market is full of them: Lenovo ThinkCentre Tiny, Dell OptiPlex Micro and HP EliteDesk Mini models. These one-litre machines often cost less than a new N100 box and come with a full desktop processor, two memory slots and a solid metal case. The trade-offs are age and power. An older Intel desktop chip draws more at load than an N100, and idle figures depend on the model and on tuning. The ThinkCentre M900 Tiny measurement above (6.1 to 7 W on Linux at 240 V) shows a well-tuned used machine can idle close to a new mini PC. Before you buy a used one: Check that it comes with its power adapter, since these machines use brand-specific connectors. Prefer a model with two memory slots and room for both an M.2 SSD and a 2.5-inch drive. Replace the thermal paste and clean the fan if the machine is several years old. Update the BIOS from the maker's support site before you install your operating system. An old laptop A laptop you already own costs nothing to try, and it has two features a mini PC lacks. Its battery keeps it running through a short power cut, and its screen and keyboard are there when the network breaks and you need a local console. It also has drawbacks: The battery. A lithium battery held at full charge, warm, for months, ages and can swell. Many laptops have a BIOS or firmware setting that stops charging below 100 percent. Use it if yours has one, and check the battery for swelling now and then. Remove a battery that has started to swell. Heat. Run it with the lid open or in a well-ventilated spot, and clean the fan. Network. Many thin laptops have no Ethernet port. A USB Ethernet adapter works, but check that Linux supports its chip. Storage. Replace a spinning hard drive with an SSD. It saves power, noise and waiting. Lid behavior. On a Linux server, tell systemd-logind to ignore the lid switch so the laptop does not sleep when you close it. Measure its idle power with a plug meter before you commit. Older laptops vary a lot, so turn the screen off before you measure. A NAS box A NAS (network-attached storage) is a small computer built around drive bays, sold with its own operating system and app store. It is the easiest way to keep several terabytes on spinning disks with redundancy. Synology's DS223j, for example, is rated at 4 W with its drives asleep and 16.31 W while being accessed, at a noise level of 18.2 dB(A). A NAS suits you if storage is the main job: file sync, photo backup, backups for the other computers in the house. It suits you less if you want to learn how the server works, because the vendor's software hides most of it, and you depend on that vendor for updates. Entry-level models also have little memory (the DS223j has 1 GB) and an Arm processor, so they run few extra services. The alternative is a mini PC or used desktop with a couple of drives and a standard Linux distribution. That takes more setup, but every part is replaceable and every program is under your control. Side-by-side comparison Storage, noise and reliability Storage. Use an SSD for the operating system and the services. Put large files on a second drive if you need the space. A single drive is a single point of failure, so plan backups from the first day: one copy on another device in the house and one copy somewhere else. RAID or a mirrored pair protects you from a failed drive, but it does not protect you from deleting the wrong folder. Noise. A server that runs all night in a living space must be quiet. Fanless boards and mini PCs are silent, small fans are audible in a quiet room, and spinning hard drives click and hum. If the machine has to live in a bedroom, choose a fanless model and SSDs. Reliability. A small uninterruptible power supply (UPS) keeps a mini PC and the router running through short power cuts and lets the server shut down cleanly in a long one. Set the BIOS to power the machine on again after a power loss, so it restarts on its own. Keep the server on a wired connection to the router, and give it a fixed address on your network, as the port forwarding guide describes. When a rented server is the better choice Hosting at home has limits that no hardware choice removes. Your upload speed caps how fast others can reach your services. Your provider may not give you a public IPv4 address, or may change it often. Nobody is on call when the power goes off while you are away. A small rented virtual private server (VPS) avoids those limits, at the cost of a monthly fee and of trusting the host with your data. It is the better choice for a service that strangers rely on, that must stay up while you travel, or that needs a fixed address. Many people use both: a home server for private services and data, and a small VPS for the public-facing parts. A low-power website shows the other route: accept that the site may go offline sometimes, and design for that. Which one to pick You own an old laptop or PC: start with it. Measure its idle power, and replace it only when you know what you need. You want a few light services at the lowest power: a Raspberry Pi 5 with 4 or 8 GB and an SSD. You want room to grow, or x86-only software: a used office mini PC or a new N100/N150 box with 16 GB of memory. Your main job is storing terabytes of files: a NAS, or a mini PC or small desktop with two drives if you prefer to run your own Linux. Whatever you choose, the next steps are the same: install a server Linux distribution such as Debian, set up SSH access with keys , and decide how the outside world will reach the machine. This page compares four ways to message people: WhatsApp, Signal, Matrix and XMPP. It looks at who runs the servers, what those servers can see, and how much work self-hosting takes, so you can decide whether a federated, self-hosted messenger is worth it for you. What you are choosing between All four encrypt messages. They differ in who runs the servers and whether those servers can talk to other servers. Centralised: one company runs every server, and you can only message people on that company's service. WhatsApp and Signal work this way. Federated: anyone can run a server, and servers exchange messages with each other, as email providers do. Matrix and XMPP work this way, so you can run a server at home and still talk to people on other servers. Encryption protects what you write. The operator of a server can still see some metadata: who has an account, who talks to whom, when, and from which IP address. The choice between these messengers is mostly a choice about who holds that metadata and how much of it they keep. WhatsApp, Signal, Matrix and XMPP compared WhatsApp WhatsApp encrypts messages and calls end to end with the Signal Protocol, according to its security whitepaper. Meta can't read your messages. What WhatsApp does collect is described in its privacy policy: information about your activity in the app, device and connection details including your IP address, and an estimate of your location. The policy says WhatsApp shares information with the other Meta companies. WhatsApp is not federated. Under the EU's Digital Markets Act, Meta announced in November 2025 that WhatsApp users in Europe can turn on chats with third-party apps, starting with BirdyChat and Haiket. It is opt-in for both sides, works only on phones, and only in Europe. You can't connect your own server to WhatsApp. WhatsApp's strength is that your contacts are already on it. That is also the reason it is hard to leave. Signal Signal encrypts all messages and calls end to end and is designed to keep as little data as possible. Its page on legal requests lists the subpoenas it has received. For each one, it says the only data it could hand over was the date an account was created and the date it last connected. The most recent entry is dated 3 November 2026. Signal is not federated, and that is a deliberate choice. In a 2016 post, Signal's founder argued that federated protocols are hard to change once deployed, so a centralised service can improve faster. The server source code is published under the AGPL, but running it gives you a separate network that can't message Signal users. You still need a phone number to sign up. Since February 2024 you can share a username instead of your number. If your main concern is keeping metadata away from the operator, and you don't need to run anything yourself, Signal is the strongest of the four. It does mean trusting one organisation and one service. Matrix Matrix is a federated protocol for chat rooms. You can run your own homeserver; Synapse is the reference server, and its latest release was 1.164.2 on 2 November 2026. Element is the best-known client. Since May 2020 it turns on end-to-end encryption by default for new conversations that aren't public. Matrix federates by replicating rooms. When a room has members on several servers, each of those servers keeps its own copy of the room's history and receives every new message. If the room is encrypted, the copies are encrypted, but every participating server still holds them. When you join a large public room from your home server, your server stores that room's history too, which costs disk space. XMPP XMPP is a federated chat protocol, standardised by the IETF; the current core specification is RFC 6120 from 2011. Its servers, such as Prosody and ejabberd, deliver messages and keep only what you configure them to keep. Your server stores your contact list, which RFC 6121 calls the roster, so the server knows who your contacts are. End-to-end encryption in XMPP is OMEMO. The Conversations README notes that only some clients implement it. The client guide lists current clients that do. The OMEMO specification says it does not protect against metadata and traffic analysis. Federation also means that the server of each contact you message sees that the message came from your address. XMPP's strength for a home server is that you control the server that holds your metadata, and you can still reach anyone on any other XMPP server. Its weakness is that the experience depends on picking good clients and enabling the right server features. The XMPP glossary explains those features. What self-hosting chat actually involves Running your own XMPP or Matrix server moves your metadata from a company to you. It also moves the work and the risk to you. Your server holds the metadata. You see your users' contact lists and connection times. If friends or family use your server, you are now the operator they trust. Uptime is your job. Messages from other servers can't be delivered while your server is down. A home connection, a power cut or a failed SD card takes your chat offline. Phones still need Google or Apple for push. On iPhone, and in the Google Play build of Conversations, a sleeping app is woken through the platform's push service via an app server run by the client's developers. In Conversations the push carries no message content. The F-Droid build of Conversations keeps its own connection open instead. Security updates and certificates. The server faces the internet, so you need to install updates and keep a valid TLS certificate for your domain. Calls need a TURN server. Reliable audio and video calls between devices behind home routers or mobile networks need a relay. The audio and video calls guide covers it. If you are prepared for that, the Prosody guide sets up a home XMPP server with the features phones need. When self-hosting chat isn't worth it Your contacts won't install anything new. A server only you use doesn't protect anyone's conversations. If the people you talk to will only use WhatsApp or Signal, ask them to use Signal. You need it to work during an emergency. A home server on one internet line and no backup power is not a good choice for messages that must arrive. You can't keep up with updates. An unpatched server on the internet is a liability. A trustworthy hosted provider is better than a neglected home server. Your goal is hiding metadata from everyone. Federation spreads some metadata to the other servers you talk to, as described above. Running your own server gives control, not invisibility. A middle path You can get most of the benefit of XMPP without running a server. Use a public XMPP provider, or point your own domain at a hosted XMPP service. The Conversations README notes that an address on your own domain lets you move between providers without changing it. You can bring the server home later and keep the same address. Moving people over The hard part of leaving WhatsApp is not the software. It is getting the people you talk to to come with you. A few things make it easier: Start with one group that wants to move, such as family or a club, instead of every contact at once. Set up their accounts and apps with them. On your own server, create the accounts yourself and give each person their address and password. Pick one client per platform for everyone, so you can answer questions. The client guide recommends one for each. Keep the old app installed for the people who don't move. Frequently asked questions Is XMPP more private than Signal? Not by default. Signal says it can only produce an account's creation date and last connection date. An XMPP server stores your contact list and sees when you message whom, so XMPP is only as private as the server you trust, which can be your own. Is XMPP better than Matrix for self-hosting? They make different trade-offs. In Matrix, every server in a room keeps a copy of that room's history, so joining large rooms costs your server disk space. An XMPP server only keeps what you configure it to keep, but the experience depends more on choosing good clients. Can I self-host Signal or WhatsApp? No. Signal publishes its server code, but a server you run can't connect to Signal's network. WhatsApp can't be self-hosted, and its third-party chats are limited to a few apps in Europe. Is WhatsApp end-to-end encrypted? Yes. WhatsApp encrypts messages and calls with the Signal Protocol. Its privacy policy says it still collects usage, device and connection data and shares information with other Meta companies. Does self-hosting XMPP stop Google or Apple seeing my messages? Message content stays encrypted, but phones still wake chat apps through Google's or Apple's push service. In Conversations these pushes carry no message content, and the F-Droid build doesn't use Google push at all. XMPP guides and client settings use a lot of short names and numbers. This glossary explains the XMPP terms you are likely to meet when you set up a server or pick a client, and says why each one matters in practice. The basics: XMPP, servers and addresses XMPP The Extensible Messaging and Presence Protocol. It is an open standard for chat, published by the IETF as RFC 6120 (the core) and RFC 6121 (messaging and contacts). Anyone can write software that speaks it, so there is no single XMPP app or company. Jabber The original name of the protocol and its network. People still say "Jabber ID" or "Jabber server", and they mean the same thing as XMPP. Server The program that holds accounts, stores contact lists and passes messages on. Prosody and ejabberd are two common XMPP servers. A server serves one or more domains, such as example.org . If you want to run one, the Prosody setup guide covers it. Client The app you chat in, such as Conversations on Android or Gajim on a computer. The client guide compares the current ones. Federation Servers talking to each other, so a user on one server can message a user on another, the way email works between providers. Clients connect to their own server on port 5222, and servers connect to each other on port 5269. If you run a server at home, other servers reach it on port 5269. JID (Jabber ID) An XMPP address. It looks like an email address: alice@example.org . The part before the @ is the localpart (the user name), and the part after it is the domain. RFC 7622 defines the format. Some clients call it a "chat address". Resource An extra part after a slash that names one connected device or app: alice@example.org/phone . Each device you log in from gets its own resource, which is how one account can be online on a phone and a laptop at the same time. Bare JID and full JID A bare JID is the address without the resource ( alice@example.org ). A full JID includes it ( alice@example.org/phone ). You give people your bare JID; the full JID only matters when software needs to reach one specific device. Contacts and online status Roster Your contact list. It is stored on your server, not on your device, so every client you log in with sees the same contacts. RFC 6121 defines it. Presence Your online status, such as available, away, do not disturb or offline, with an optional status message. Your server sends your presence to the contacts allowed to see it. Presence subscription Permission for a contact to see your presence. When you add someone, you ask to subscribe to their presence, and they approve or decline. A mutual subscription also helps encrypted chat, because clients use it to find each other's encryption keys. If you are still deciding whether XMPP is right for you, the comparison with WhatsApp, Signal and Matrix covers what your server can and can't see. Group chats MUC (multi-user chat) A group chat room, defined in XEP-0045 . A room has its own address, such as garden@rooms.example.org , and usually lives on a separate service of the server. Clients often just call it a "group chat" or "channel". Nickname The name you use inside one room. It can differ from your account name and from room to room. Affiliation and role The two sets of rights in a MUC room. Affiliation is lasting (owner, admin, member, outcast, which means banned). Role applies to the current visit (moderator, participant, visitor) and decides who may speak or remove others. Public and private rooms A public room is listed and open to anyone. A private, members-only room only admits people on its member list. End-to-end encrypted group chat with OMEMO needs a private room in which members can see each other's real addresses. MIX Mediated Information eXchange ( XEP-0369 ), a proposed successor to MUC. It is still at Experimental status, and the common clients and servers use MUC for group chats. RFCs, XEPs and compliance RFC A standard published by the IETF. The XMPP core is in RFCs 6120, 6121 and 7622. XEP (XMPP Extension Protocol) A numbered document that adds one feature to XMPP, such as file upload or message history. The XMPP Standards Foundation publishes them, and XEP-0001 describes the process. When a client or server lists "supported XEPs", this is what it means. XEP status Each XEP carries a status. Experimental means it is still being worked out and may change. Stable means the XMPP Council has approved it and it is safe to build on; some lists still show this status by its older name, Draft. Final means it is finished. Deferred means it has had no recent activity. Status does not tell you how widely a XEP is used: push notifications (XEP-0357) are Deferred and OMEMO (XEP-0384) is Experimental, yet Conversations and Monal both support them. Compliance suites XEPs that list which other XEPs a client or server should support for a given use, such as mobile chat. The most recent is XEP-0479 (Compliance Suites 2023). The Conversations compliance tester checks a live server against a similar list. Service discovery (disco) How a client asks a server what it supports ( XEP-0030 ). This is what a client reads when it shows you "server info". Features that make chat work on a phone A phone switches networks, sleeps and loses its connection often. These extensions make that invisible. If your server lacks one of them, the symptom is usually missed messages or notifications that don't arrive. Carbons Message Carbons ( XEP-0280 ) send a copy of every message to all your online devices, including messages you sent from another device. Without carbons, a chat you answer on your laptop looks unanswered on your phone. MAM (message archive management) Server-side message history ( XEP-0313 ). The server keeps your messages for a time you configure, and a client that was offline fetches what it missed. It is also how a new device gets your recent history. Stream management XEP-0198 lets a client resume a dropped connection quickly and makes sure no message gets lost in between. It matters most on mobile data. Push notifications XEP-0357 lets the server wake a sleeping phone app when a message arrives. On Android and iPhone this goes through an app server run by the client's developers and then through Google's or Apple's push service. In the Conversations app, the push message is only a wake-up signal with no content. In Prosody the server side is mod_cloud_notify ; in ejabberd it is mod_push . CSI (client state indication) XEP-0352 lets a client tell the server when the app is in the background, so the server can hold back unimportant traffic such as status changes and save battery. HTTP file upload XEP-0363 is how pictures and files are shared. The client uploads the file to a web address the server provides and sends the link. The recipient can download it later, even if the sender is offline. The server needs disk space for these files and a limit on their size. PEP (personal eventing protocol) A small store on your account where clients publish data for your contacts, such as your avatar or your OMEMO keys ( XEP-0163 ). OMEMO doesn't work without it. Bookmarks Your saved list of group chats, stored on the server so every client joins the same rooms ( XEP-0402 ). Encryption TLS (transport encryption) Encryption of the connection between your client and your server, and between servers. It stops anyone on the network from reading messages in transit, but each server can read messages it handles. Your server needs a valid certificate for its domain. End-to-end encryption (E2EE) Encryption on the sender's device that only the recipient's devices can undo. Servers pass the message on but can't read it. OMEMO The end-to-end encryption that most current XMPP clients use ( XEP-0384 ). It works with several devices per person and when the contact is offline. The specification says it does not protect against metadata and traffic analysis, so your server still sees who you talk to and when. Fingerprint A short code that identifies one device's encryption key. Comparing fingerprints with a contact, in person or by scanning a QR code, proves that the key belongs to them. BTBV (blind trust before verification) A trust policy used by Conversations and other clients. New keys are trusted automatically until you verify one of a contact's keys by fingerprint. After that, only verified keys are trusted. OpenPGP and OX Older and alternative ways to encrypt XMPP messages with PGP keys. OX is the newer OpenPGP for XMPP. They are less common than OMEMO; Profanity supports both. OTR (off-the-record) An older end-to-end encryption scheme for one-to-one chats. A few clients still support it, among them monocles chat and Profanity. Calls Jingle The XMPP way of setting up a direct session between two devices ( XEP-0166 ), used for audio and video calls ( XEP-0167 ) and for some file transfers. The call itself travels between the devices, not through the XMPP server. STUN and TURN Helpers for calls between devices behind home routers or mobile networks. A STUN server tells a device its public address. A TURN server relays the call when the devices can't reach each other directly. coturn is a common TURN server, and the audio and video calls guide sets it up. External service discovery XEP-0215 lets the XMPP server hand clients the address and temporary login for its STUN and TURN service, so users don't have to configure them. Server add-ons Module A plug-in that adds a feature to the server. In Prosody, most XEPs above are modules you switch on in the configuration, such as mod_mam for message history. Component A separate program that connects to the server and handles its own subdomain, using the component protocol ( XEP-0114 ). Group chat services, file upload services and gateways are often run as components. Gateway (transport or bridge) A component that connects XMPP to another network, such as SMS, IRC or another chat service, so you can reach those users from your XMPP client. XEP-0100 describes how clients register with one. Cheogram on Android is built around gateways to phone numbers. In-band registration Creating an account from inside a client ( XEP-0077 ). Public servers often allow it. On a home server it is usually safer to turn it off and create accounts yourself, so strangers can't sign up. Frequently asked questions What is a JID in XMPP? A JID, or Jabber ID, is an XMPP address such as alice@example.org. A version with a slash and a device name after it, such as alice@example.org/phone, is a full JID and points to one logged-in device. Is Jabber the same as XMPP? Yes. Jabber is the original name of the protocol and network, and XMPP is the name of the open standard. What does XEP stand for? XEP stands for XMPP Extension Protocol. Each XEP is a numbered document from the XMPP Standards Foundation that adds one feature, such as file upload or message history. What is MUC in XMPP? MUC means multi-user chat, the group chat rooms defined in XEP-0045. Each room has its own address and usually runs on a separate service of the server. What is the difference between MAM and carbons? Carbons copy each message to all your devices that are online right now. MAM stores messages on the server so a device that was offline can fetch what it missed. Does OMEMO hide who I talk to? No. OMEMO encrypts the content of messages, but the XEP-0384 specification says it does not protect against metadata and traffic analysis, so your server still sees who you talk to and when. API compatibility: OpenAI and Anthropic endpoints Ollama has its own API under /api/ , such as /api/chat , and an OpenAI-compatible API under /v1/ . Its responses include the load time, the prompt time and the generation time. LM Studio has an OpenAI-compatible API under /v1/ , including /v1/chat/completions , /v1/responses and /v1/embeddings . It also has its own REST API under /api/v1/ , which can load, unload and download models, and an Anthropic-compatible /v1/messages endpoint . Programs that speak the OpenAI API can use either tool by changing the base URL and the model name. LM Studio also has an Anthropic-compatible endpoint. Licence: Ollama is open source, the LM Studio app is not Ollama is open source under the MIT licence . The LM Studio app is closed source. Since July 2025 , LM Studio is free to use at home and at work, and its terms allow personal and internal business use. The lms command-line tool and LM Studio's JavaScript and Python SDKs are MIT licensed. If you prefer open-source software on your server, that settles the choice: Ollama. Which one to run on a home server Choose Ollama for a server that runs all the time with one user or a few. It has an official GPU image, frees memory after 5 minutes without requests, is open source, and was the faster of the two in this test. Choose LM Studio on a desktop where you want a graphical app to find and try models, or when several people or programs send requests at the same time and you want that to work with the defaults. Its desktop app for Linux comes as an AppImage and a .deb package; this test used only the headless daemon. Use both if you like, with one set of GGUF files: link them into LM Studio and import them into Ollama. Ollama's copy of the two test models used 22.4 GB of extra disk space. Neither tool is a good fit for a small server without a GPU if you want quick answers from models this size. The hardware guide covers what each type of machine can do. Frequently asked questions Is LM Studio faster than Ollama? Not in this test. On an RTX 3090 with the same GGUF files, Ollama 0.40.15 generated about 10% faster with Qwen3.5 9B and about 5% faster with Qwen3.5 27B. LM Studio started short answers sooner, and with its defaults it handled four requests at once faster, most clearly on the 27B model (90 against 33 tokens per second). Do LM Studio and Ollama use the same engine? On Linux with GGUF models, yes. Both start llama.cpp's llama-server , but they ship different llama.cpp builds and start it with different options, such as context size, batch size and parallel slots. Can LM Studio and Ollama share the same model files? Yes. LM Studio can link to an existing GGUF file with lms import -l , and Ollama can import the same file through a Modelfile. Ollama stores a copy in its own folder, so the file takes disk space twice. Can LM Studio run headless or in Docker? Yes. Its headless daemon, llmster , runs without the app, and the lmstudio/llmster-preview Docker image is a preview that supports only the CPU. In this test it ran on an NVIDIA GPU after downloading the CUDA runtime with lms runtime get --allow-incompatible , which LM Studio does not support. Why is LM Studio using the CPU instead of the GPU? In the official Docker image, the only runtime is the CPU build of llama.cpp, so LM Studio reports "No GPUs detected". After a CUDA runtime was downloaded and selected with lms runtime select , LM Studio listed the RTX 3090 and the model ran on the GPU. Is LM Studio open source? No. The app is closed source but free for home and work use. Its lms command-line tool and SDKs are MIT licensed, and Ollama is open source under the MIT licence.
